# v1.31 research production: optional breakdown pointer and numeric dataflow

Static original machine-code inspection of official locally supplied `ORION2.EXE` v1.31 (SHA-256 `4e11be14217b4aafa1839f333bf5eba037f98b0c44e9e4752c96c464c260419f`) found a conditional dataflow from the **optional output-breakdown buffer** back into the **numeric research-production worker accumulator**.

The original `Colony_Job_Production_` function at CODE `0xCE280` zeroes a `0x256`-byte local breakdown at `EBP-0x4D4` and passes it as ECX to `Colony_Pop_Base_Prod_Produced_` only when the external output pointer is non-null (`0xCE3E2–0xCE3FA`). Research dispatch selects `Colony_Empire_Base_Research_Produced_`, which passes that pointer in EBX to original `Colony_Research_Per_Scientist_` when requesting a fresh detailed result. For planet BYTE `+0x0F` code 10 or 11, that helper normally adds 2 or 5 to its result and **additionally writes 2 or 5 into DWORD at breakdown offset `+0x226`**, when EBX is non-null. The original job function then reads DWORD `EBP-0x2AE` as a separate numeric component at CODE `0xCE609`. The offsets identify the **same storage**: `-0x4D4 + 0x226 = -0x2AE`.

Consequently, the instruction-level trace contains a candidate **reporting-dependent numeric path**: when the original temporary breakdown was not passed, this local component remains zero; when passed and the original planet-code branch fires, it gains 2 or 5. For a controlled synthetic job 2 example (eligible one-population tag, no other flags, base 5, gravity factor 2, government group 0, settings scalar +8), the signed research result differs as `IDIV((8+10),20)=0` versus `IDIV((10+10),20)=1`. Planet code 11 has a parallel synthetic path.

This is **not yet a confirmed game bug**. The two states are constructed from verified source predicates, not from verified reachable official DOS savegames, and no original runtime differential check was executed. The finding is recorded because accidentally making breakdown-output a numeric no-op in a native rewrite could depart from verified original instruction behavior. A source-visible discrepancy is not permission to change gameplay: confirm valid-state reachability, DOS output, and a user-authorized change decision if fixing rather than preserving it.
